# NearBook 고도화 분석 — 2026-10-12

## 결론

우리동네책은 기능이 부족한 초기 랜딩 페이지가 아니다. 검색·도서관 지도·도서 큐레이션·위시리스트·기본 도서관·이메일/푸시·바코드 스캔·PWA·SEO 기반이 이미 있다.

지금 우선순위는 **새 기능 추가보다 기존 핵심 경로의 정상화와 데이터 신뢰도 확보**다. 제품의 중심을 “읽고 싶은 책을 찾아, 가까운 도서관에서 빌리는 행동으로 연결”에 맞추는 것을 권한다.

권장 순서: **운영 데이터 경로 복구 → 검색/위치/대출 확인 UX → 찜·알림 재방문 → 검색 유입 확대**.

## 분석 범위와 한계

- 운영 사이트 `https://www.near-book.com/`에서 비로그인 화면을 실제 탐색했다.
- 홈, 검색, 책 상세, 도서관 목록/지도, 도서관 상세, 인기 도서, 분야별 도서/소설, 탐색, 신착도서, 로그인 진입, FAQ, 피드백 폼을 확인했다.
- 공개 GET API와 페이지 결과를 대조했다. 피드백 제출·찜 추가·알림 변경·배포·설정 변경은 하지 않았다.
- 소스 기준은 로컬 `main`, HEAD `76d6265`. 운영 배포가 이 커밋과 완전히 같다는 것은 별도로 확인하지 않았다.
- 로그인 이후 기능, 카메라/GPS 권한, 푸시 수신, 이메일 발송은 소스 기반 검토다. 실사용 계정이나 개인정보를 입력하지 않았다.
- 실제 모바일 기기에서 검증하지 않았다. 브라우저 viewport override를 시도했지만 실제 너비가 1920으로 유지되어 모바일 실측으로 취급하지 않았고 override는 해제했다.
- 로컬 의존성과 pnpm 실행 환경이 확인되지 않아 빌드·자동화 테스트는 실행하지 않았다. 소스 변경은 없고 이 보고서만 추가했다.
- API 도메인 직접 탐색은 브라우저의 `ERR_BLOCKED_BY_CLIENT`로 제한됐다. API 자체 인증서 장애를 단정하지 않는다.
- 아래의 “실측”은 이번 운영 화면/API 관찰, “소스”는 정적 코드 분석, “추정”은 추가 로그 검증이 필요한 가설이다.

### 유지할 장점

- 녹색 중심의 브랜드, 책·도서관이라는 명확한 서비스 메시지.
- 검색과 도서관 열람을 비로그인으로 제공하는 구조.
- Next.js App Router, NestJS 모듈, PostGIS 거리 검색 등 목적에 맞는 기술 구성.
- canonical, JSON-LD 안전 직렬화, 운영/preview 색인 구분, sitemap 수집과 테스트가 이미 구현돼 있음.
- 위시리스트/기본 도서관/알림/피드백까지 마련돼 있어 새 제품으로 재작성할 필요가 없음.

## 실제 운영에서 발견한 문제

### P0-1. 데이터가 있는데 상세 페이지는 “없음”으로 표시

**실측**

- `/search?q=불편한 편의점`에서 49건이 표시됐다.
- 결과의 일반판 `9791161571195`를 클릭하면 `/book/9791161571195`에서 “책을 찾을 수 없습니다 / ISBN이 잘못되었거나 정보나루에 등록되지 않은 책입니다.”가 나왔다.
- 그런데 `/api/books/9791161571195`는 정상 책 메타데이터를 반환했다.
- `/api/books/9791161571195/with-libraries?lat=37.5665&lng=126.978`도 책 객체와 제휴 목록을 반환했다. `libraries`는 빈 배열이었다. 이것만으로 실제 미소장 여부는 판단할 수 없다.
- 홈 목록의 서울도서관을 누르면 `/library/111314`에서 “도서관을 찾을 수 없습니다”가 나왔다.
- `/api/libraries/111314`에는 서울도서관의 이름·주소·운영시간 등 정상 데이터가 있었다.

**소스**

- `apps/web/app/book/[isbn]/page.tsx`: 실패한 fetch를 `null`로 바꾸고 `notFound()` 처리한다. 메타데이터에도 `noindex`가 붙는다.
- `apps/web/app/library/[id]/page.tsx`: 요청 실패나 모든 non-OK 응답을 `notFound()`로 처리한다.
- 책 상세는 메타데이터와 위치 기반 보유 현황/제휴를 한 요청에 묶고 30일 revalidate를 사용한다. 도서관 상세는 1주다.

**추정 및 확인할 사항**

브라우저에서 성공하는 API 경로와 서버 렌더링의 upstream 경로/환경변수/인증서 연결, 그리고 이전 실패 결과의 캐시가 다를 수 있다. 정확한 원인은 Vercel 서버 로그, 실제 배포 커밋/환경변수, upstream 응답과 캐시 상태를 함께 확인해야 한다. “정보나루에 책이 없다”나 “DB에 도서관이 없다”로 단정하면 안 된다.

**권장 변경**

1. 책 기본 정보 fetch와 위치·대출 상태, 분석·제휴 데이터를 분리한다. 부가 기능 실패가 책 존재 자체를 숨기면 안 된다.
2. 실제 404, timeout, TLS/네트워크 오류, 429, 5xx를 구분한다.
3. 일시 장애는 재시도 가능한 안내와 마지막 정상 데이터를 보여준다. 존재하는 자산에 장애 때문에 잘못된 not-found/noindex를 만들지 않는다.
4. 메타데이터는 긴 캐시, 대출 가능성은 짧은 캐시/클라이언트 재조회로 분리한다. 서울 기본 좌표에서 초기 데이터를 그대로 쓰는 경로도 오래된 가용성을 고착시키지 않도록 한다.
5. 배포/캐시 재생성 후 대표 ISBN과 대표 도서관을 웹 화면까지 검증한다. GET API 성공만으로 복구 완료로 보지 않는다.

### P0-2. 페이지·프록시·브라우저의 API 연결이 불일치

**실측**

- 홈의 주변 도서관 목록은 최종적으로 정상 표시됐다.
- `/libraries`에서는 지도 타일은 보이지만 “도서관 목록을 불러오지 못했습니다”가 표시됐다.
- 서울 기본 bounds로 `/api/libraries/in-bounds`를 열면 `{"error":"upstream 오류"}`가 나왔다.
- `/popular`는 빈 안내를 보여주지만 `/api/books/loan-item?limit=2`에는 실제 인기 대출 도서 2권이 있었다.
- `/category`, `/category/novel`, `/new-books`에서도 빈 안내를 확인했다. 이 세 화면 각각의 전체 upstream 데이터를 검증한 것은 아니다.

**소스**

- `apps/web/lib/constants.ts`: server base가 `INTERNAL_API_URL → PUBLIC_API_BASE_URL` 순서로 떨어진다. public 값이 상대 경로라면 server fetch에 안전하지 않다.
- `apps/web/next.config.ts`: rewrite는 `INTERNAL_API_URL`을 우선 사용한다.
- `apps/web/app/api/libraries/in-bounds/route.ts`, `region-center/route.ts`: 서버에서 `PUBLIC_API_BASE_URL`로 fetch한다. server base와 다를 수 있다.
- `apps/web/app/api/analytics/event/route.ts`: 공통 상수와 다른 자체 fallback 로직을 갖고 있다.
- 페이지별 `fetch`가 흩어져 있고 응답 형태도 bare object, array, `{data}`, `{data, meta}`가 혼재한다.

**권장 변경**

- 브라우저용 base와 서버용 절대 upstream을 명확히 분리하고, server fetch는 서버 전용 모듈 하나를 사용한다.
- 상대 URL·빈 URL·잘못된 production 값은 배포 전 환경 검증으로 차단한다.
- 같은 경로에 Next Route Handler와 rewrite를 겹쳐 사용한 부분을 정리한다. 서버용 upstream 호출에 브라우저 base를 쓰지 않는다.
- timeout·응답 상태·API 오류 타입·응답 스키마 검증을 공통화한다.
- 정상 빈 결과, 장애, 갱신 중, 오래된 데이터라는 상태를 사용자에게 구분해서 보여준다.

## 데이터 신뢰도와 기술적 위험

### P0/P1. 조회 실패를 미소장으로 처리

`apps/api/src/modules/libraries/libraries.service.ts`에서 외부 보유 조회 실패를 `holdingCount: 0`, `loanAvailable: 0`으로 바꾸거나 결과에서 제외한다. 따라서 외부 장애가 “가까운 곳에 책 없음”처럼 보일 수 있다.

권장 응답 상태는 최소 `available / borrowed / not_held / unknown`이다. `checkedAt`, `source`, `stale`, 확인한 도서관 수를 같이 내려야 한다. `unknown`은 미소장으로 숨기지 말고 재확인/공식 사이트 링크를 제공한다.

지금 보유 API의 Y/N을 1/0으로 변환해 “1권 대출 가능”이라고 보여준다. 실제 권수 데이터가 아니라면 수량 대신 “대출 가능”이라고 표시해야 한다. 5km 안에 도서관이 없다는 것과 보유 책이 없다는 것도 다른 상태다.

### P1. 도서관 행동 버튼이 핵심 화면에서 연결되지 않음

- `apps/web/components/library/library-card.tsx`는 `reservationUrl`, `directionsUrl`이 있어야 공식 사이트/길찾기 버튼을 렌더한다.
- `apps/web/app/book/[isbn]/_components/library-status.tsx`는 두 값을 전달하지 않는다.
- 주변 도서관의 홈페이지/좌표 데이터를 활용해 직접 연결하면 상세 → 도서관 상세 → 홈페이지라는 불필요한 단계를 줄일 수 있다.
- 예약/책별 검색 URL은 지원하는 도서관만 매핑한다. 지원하지 않는 곳은 홈페이지로 안내하고 자동 예약을 암시하지 않는다.
- 서울도서관 공개 응답의 운영시간은 `{text, closed}`였지만 상세 화면은 `operatingHours.weekday`만 본다. 공용 `Library` 타입은 문자열로 선언돼 있다. 스키마를 통일하고 운영시간과 휴관일을 실제 응답에 맞게 노출해야 한다.

### P1. 검색 품질·정렬·페이지 정합성

**실측**: ‘불편한 편의점’의 필사집·북투어가 상위에 있고 일반판은 첫 페이지 9번째였다. ‘공룡 편의점’ 같은 느슨한 관련 결과도 섞였다.

**소스**

- 한국어 토큰은 단어 + bigram/trigram이다. 부분 토큰의 일치만으로 관련성이 약한 책이 섞일 여지가 있다.
- “도서명” 유형에서도 Orama는 title뿐 아니라 author/publisher를 검색한다.
- 검색은 Orama 결과 이후 정보나루를 동기 호출한다. 외부 timeout이 검색 응답까지 지연시킬 수 있다.
- 반환 `total`은 remoteTotal, 페이지의 항목은 로컬 검색 인덱스다. 두 집합이 달라 빈 페이지·건수 불일치 가능성이 있다.
- 인기 점수는 일간 cron에서 반영되지만 일반 book-cache upsert는 기본 0을 쓰므로 덮어쓰기/리빌드 후 점수 유지 여부 검증이 필요하다.
- 검색용 Map은 TTL 검사는 있지만 max size/만료 엔트리 정리가 없다.

**권장 변경**

- 정규화된 제목의 정확 일치·전체 구문 일치를 최우선으로 하고, 부분/오타 매칭은 이후에 적용한다.
- ISBN 자동 감지, ISBN-10/13 정규화, 저자명 역할 표기 제거, 판본/큰글자/필사집 구분을 추가한다.
- 제목 검색과 저자 검색의 의미를 실제로 맞춘다. 원한다면 “통합 검색”을 별도 기본 유형으로 제공한다.
- 먼저 로컬 결과를 빠르게 반환하고 외부 보충은 dedupe된 작업으로 처리한다. 반영 후 결과 캐시 무효화/재조회 흐름을 만든다.
- total과 항목이 같은 결과 집합에 속하도록 한다. 아직 보충 중이면 확정 총건수처럼 표시하지 않는다.
- 대표 검색어 30~50개에 기대 결과/순위를 정의해 회귀 테스트를 만든다. ‘불편한 편의점’, ‘한강’, ISBN, 붙여쓴 제목, 짧은 검색어, 판본 중복을 포함한다.
- max size 있는 캐시와 동일 요청 동시 실행 방지(single-flight)를 적용한다.

### P1. 오류 상태가 UI로 전달되지 않음

- `search-page-inner.tsx`는 SWR의 error를 꺼내지 않고 `ResultList`의 error prop에도 전달하지 않는다.
- fetcher는 non-OK 응답을 throw하지 않는다. API `SearchService`도 예외를 0건 결과로 반환한다.
- API 오류, 파싱 오류, 실제 0건을 같은 “검색 결과 없음”으로 표시할 수 있다.
- 찜/알림/삭제 등 쓰기 동작의 예외 안내·중복 클릭 방지·저장 실패 복구도 함께 정리할 필요가 있다.

### P1. PWA 개인 데이터 캐시 분리

`apps/web/public/sw.js`는 `/api/*` GET과 성공한 navigation 응답을 포괄적으로 캐시한다. `/me/*`, 인증/계정 API에 대한 제외 조건이나 로그아웃 시 캐시 초기화가 없다.

같은 브라우저에서 로그아웃/계정 변경 후 오프라인으로 이전 개인 데이터를 보여줄 위험이 있다. 실제 계정 재노출을 재현한 것은 아니며 코드상 위험 평가다.

공개 정보만 allowlist 방식으로 캐시하고, 개인화/인증 응답은 캐시하지 않는다. 공개 대출 상태에도 TTL·오프라인·최종 확인 시각을 표시한다. 이미지/페이지 캐시의 크기 상한과 정리 전략도 필요하다.

### P1. 알림 채널 독립성·실제 주기

- UI에는 “즉시 알림, 이메일보다 빠름”이 있지만 `WishlistDigestCron`의 푸시는 이메일과 같은 새벽 4시 작업에서 발송된다.
- 후보 사용자 조회가 `emailOnAvailable = true`, active email status, email 존재 조건으로 제한된다. 소스상 이메일을 꺼두고 푸시만 켠 사용자는 이 경로의 발송 대상에서 제외될 수 있다.
- 알림 cron은 400/500 기준, 정보나루 client/QuotaService는 기본 30,000 기준 등 한도 정책이 분산돼 있다. 숫자는 실제 계정 한도를 확인한 뒤 하나로 통일해야 한다.
- `QuotaModule`/`QuotaService.acquire()`와 pending lookup cron 코드는 존재하지만 현재 모듈 등록/호출 연결이 확인되지 않았다. 파일 존재를 운영 기능 동작으로 간주하면 안 된다.

채널별 opt-in/대상 조건/결과 로그를 독립시키고, 실제 발송 주기에 맞춰 문구를 고친다. 즉시 알림이 정말 필요하다면 호출 예산과 중복 방지를 설계한 별도 주기 작업이 필요하다.

## UI/UX 고도화 제안

### 홈: 검색과 기준 지역을 첫 화면으로

현재의 큰 소개 문구 아래에 주요 검색창을 배치하고, 옆이나 바로 아래에 “서울 시청 주변 · 변경”처럼 실제 검색 기준을 표시한다. GPS를 쓰지 않았는데 “현재 위치: 서울 전체”와 0km를 보여주면 실제 사용자 위치로 오해할 수 있다.

추천 구성:

1. 짧은 가치 제안 + 큰 검색창 + ISBN 스캔 진입.
2. 기준 지역/내 도서관 선택. GPS 없이 시군구/도서관 이름으로 설정 가능.
3. 최근 검색·최근 본 책 또는 찜한 책의 상태.
4. 내 도서관 신착/가까운 곳에서 빌릴 수 있는 책.
5. 전국 인기/급상승은 보조 탐색.

소스상 홈 위치 안내는 `status === 'idle' && !isLocationLoaded`일 때만 나와 초기 storage 로드 후 사라진다. 일반 방문자가 설정을 바꿀 수 있는 명확한 버튼을 상시 제공하는 것이 좋다.

### 검색: 책 선택을 빠르게

- 정확 제목 결과 우선, 판본 라벨과 동일 작품 묶음.
- 제목 긴 문자열을 한 줄 truncate로 숨기지 않고 구분 가능한 정보 제공.
- 저자/ISBN 자동 감지와 검색 유형 설명.
- “내 도서관 우선 / 대출 가능한 곳” 옵션은 보유 데이터 연결 후 추가.
- 모든 검색 결과마다 다수 외부 API를 즉시 호출하지 않는다. 관심 결과/화면에 보이는 결과부터 배치·캐시로 확인한다.
- loading 중 0건을 확정 건수처럼 표시하지 않는다.
- 자동완성의 키보드 탐색·Esc·ARIA combobox 상태와 모바일 긴 제목을 검증한다.

### 책 상세: 대출 행동이 최우선

책 정보 아래 첫 섹션에서 선택한 지역/기본 도서관, 대출 가능 상태, 거리, 최종 확인 시간을 보여준다. 도서관에서 확인·길찾기·찜/알림으로 다음 행동을 분명히 만든다.

보유가 없으면 반경 확장(5 → 10 → 20km), 다른 지역/판본 선택, 알림 저장, 공식 도서관 확인이라는 대안을 제공한다. 분석/추천·광고·구매 옵션은 핵심 확인 아래 둔다. 제휴 검색 링크가 있다는 것과 해당 플랫폼에 실제 책이 있다는 것은 구분한다.

### 내 도서관·위시리스트: 재방문 이유 만들기

- 처음 저장할 때 기본 도서관 선택까지 자연스럽게 연결한다.
- 위시리스트를 단순 표지 목록이 아니라 “내 도서관에서 대출 가능 / 대출 중 / 확인 불가” 작업 목록으로 발전시킨다.
- 상태 변화 알림을 제공할 때 마지막 확인 시각과 도서관 공식 링크를 함께 보여준다.
- 비로그인 최근 검색/최근 본 책/임시 찜을 로컬에 저장하고 로그인 후 병합하는 것은 P2 실험으로 검토할 수 있다.
- 현재 free 위시리스트 10권/도서관 1개 한도와 동작이 없는 “Pro 알아보기” UI는 가치 검증 단계에서 가입·재방문을 막을 수 있다. 결제 흐름이 없다면 유료 CTA를 먼저 완성하거나 감춘다. 요금 정책 변경은 별도 제품 결정이다.

### 모바일

코드상 모바일 검색은 아이콘/Sheet에 들어가 있으므로 홈 본문의 큰 검색창이 특히 중요하다. “검색 / 내 도서관 / 찜”이라는 세 가지 핵심 목적을 모바일에서 한두 번의 조작으로 접근하게 한다.

지도만을 기본 뷰로 강제하기보다 목록 우선 또는 마지막 선택을 저장한다. 360/390/430px에서 시도·시군구 필터/지도·목록 버튼, 긴 책 제목, 설치 배너와 하단 CTA 겹침, 키보드 열린 상태를 실기기로 검증한다. 기존 PWA 설치 배너는 유용한 행동을 완료한 뒤 노출하는 편이 낫다.

## 아키텍처와 운영 개선

현재 구조는 `Next.js(Vercel) → NestJS(Oracle/Docker) → PostgreSQL/Supabase/PostGIS + Orama + 정보나루/알라딘`이다. 이를 유지하고 경계를 정리하는 것을 권한다. 당장 마이크로서비스 전환이나 검색 엔진 교체부터 할 필요는 없다.

- 서버 API client, 공개 브라우저 client, 인증 client 분리. 공개 검색이 매번 세션 refresh에 의존하지 않게 한다.
- 실제 API DTO와 공용 타입 정합성 확보. 특히 operatingHours, 보유 상태/권수, 확인 시각, error envelope.
- 두 개의 `CacheService`를 통합하거나 책임을 명확히 분리한다. 현재 서로 다른 클래스/인스턴스라 health의 memorySize가 전체 캐시 상황을 대표하지 않는다.
- 큐레이션 데이터의 기준 기간, 마지막 성공 갱신, 건수, 오류를 운영 지표로 노출한다. “매일 갱신” 고정 문구 대신 실제 확인 가능한 최신성을 사용한다.
- 외부 API 호출 예산·우선순위·타임아웃·재시도·중복 방지를 한 경로로 묶는다. 처음에는 DB-backed 작업 큐와 단일 프로세스로도 충분하고 Redis/별도 워커는 운영 규모에 따라 결정한다.
- Orama `/data` 경로는 Dockerfile에 있으나 CD의 `docker run`에 persistent volume이 없다. 컨테이너 재생성 시 디스크 인덱스가 사라져 rebuild하게 될 수 있다. 영속 볼륨 또는 명시적 rebuild 전략을 선택한다.
- 검색 full rebuild는 새 인덱스를 완성한 뒤 원자적으로 교체하고, popularity/delta 반영의 watermark와 실패 재처리를 둔다.
- `/health`는 프로세스 응답 확인이며 DB/검색 준비 상태를 검증하지 않는다. liveness와 readiness를 분리한다.
- CD는 latest pull 후 기존 컨테이너를 중단·삭제하고 새 컨테이너를 실행한다. 새 인스턴스 준비 확인, smoke test, 커밋 태그 기반 롤백을 추가한다.
- SSL 만료/HTTP 상태만이 아니라 대표 검색 → 책 상세 → 도서관 링크까지 읽기 전용 모니터링한다. 실제 알림 수신처 추가는 운영자 승인을 받아 설정한다.

## 계측과 성장

Vercel Analytics와 자체 행동 이벤트/SQL 운영 문서는 이미 있다. 새로운 분석 도구를 추가하기 전에 기존 이벤트의 의미를 바로잡는 것이 먼저다.

- 헤더 `SearchBar`는 검색 페이지로 이동하지만 `search_submit`을 기록하지 않는다. 검색 페이지의 별도 SearchBar만 해당 이벤트를 기록해 유입 경로별 검색 전환율이 누락될 수 있다.
- `library_status_view`는 초기 데이터가 비어도 발생한다. 이를 도서관 확인 성공과 동일하게 보면 실패를 성공으로 셀 수 있다.
- 이벤트의 `availableCount`는 `loanAvailable`이 아니라 `holdingCount > 0`을 센다. “보유 도서관 수”와 “대출 가능한 도서관 수”를 분리한다.
- `book_result_click`에 순위·필터, 조회에 duration/status/freshness, 공식 사이트 이동에 목적을 추가하면 개선 효과를 판단하기 쉬워진다.
- 방문 → 검색 → 책 선택 → 조회 완료 → 대출 가능 발견 → 공식 사이트 이동/찜 → 7일 재방문을 별도로 측정한다.
- 좋은 핵심 지표는 “유효한 대출 가능 정보를 확인하고 다음 행동으로 이어진 사용자 수”다. 조회 성공이지만 0건인 경우도 별도 정상 결과로 집계한다.

SEO는 이미 상당 부분 정리돼 있다. 이번 상세 오류/빈 화면이 해결되지 않으면 메타태그 추가보다 콘텐츠 정상 렌더링이 우선이다. 이후 실제 도서관 데이터가 있는 지역 랜딩, 도서관별 신착·인기, 책별 대출 가능 탐색, 공유용 OG 카드, 소규모 독서/지역 커뮤니티 실험을 순서대로 적용한다. 기존 SEO 계획의 과거 숫자를 현재 수치로 재사용하지 않는다.

### 처음 실행할 작은 작업 묶음

1. Vercel 현재 production 환경과 서버 로그를 읽어 페이지/API 불일치 원인을 확정한다. 비밀값은 노출하지 않는다.
2. server/public base 분리와 지도 proxy 수정, 오류를 not-found로 바꾸지 않는 처리.
3. 책 메타와 주변 도서관 상태 분리. 대표 책·도서관 페이지를 실제 브라우저로 검증.
4. 홈 본문 검색창과 지역 변경, 도서관 CTA 연결.
5. 위 흐름을 재현하는 테스트와 읽기 전용 운영 smoke check.

CI에는 이미 lint/type-check/build/test 단계가 있다. 문제는 테스트 명령 부재가 아니라 커버리지다. 발견한 테스트는 주로 웹 SEO/API-base 관련이며 API는 health 테스트 1개다. 검색→책→도서관, 외부 API 실패, GPS 거부, 로그인/찜, 채널별 알림, 계정 변경/오프라인이라는 실제 서비스 동작 테스트를 추가해야 한다.
